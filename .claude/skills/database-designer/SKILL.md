# Database Designer (TimeTrace)

One SQLite file: `~/.timetrace/timetrace.db` (override with `TIMETRACE_DB_FILE`). SQLModel defines the tables in `src/timetrace/db/models.py`; Alembic owns the schema history in `src/timetrace/db/migrations/versions/`.

## The non-negotiable rule

**Every change to `db/models.py` ships with a migration in the same commit.**

`run_migrations()` (`db/session.py`) runs `alembic upgrade head` on every daemon boot, and it deliberately no longer swallows failures — the old swallow-and-stamp fallback is what produced a ghost revision in the live DB (see CLAUDE.md). A model change without a migration is a boot crash on the user's machine, or silent drift.

```bash
uv run timetrace db revision -m "add session.timezone"   # autogenerate
uv run timetrace db migrate                              # apply (also runs on daemon boot)
```

Always **read and edit** the autogenerated file. SQLAlchemy's SQLite autogenerate misses server defaults, misjudges nullability, and cannot express a type change at all.

## Model conventions

```python
class Thing(SQLModel, table=True):
    id: str = Field(default_factory=generate_uuid7, primary_key=True)   # UUIDv7 string, never int
    owner_id: str | None = Field(default=None, foreign_key="thing.id")  # FK target is lowercase classname.id
    name: str = Field(index=True)
    created_at: datetime = Field(default_factory=utc_now)               # naive-UTC on disk
```

- PKs are `str` UUIDv7 (`generate_uuid7()`), time-ordered so `ORDER BY id` is still chronological and B-tree inserts stay local.
- Table names are the lowercased class name (`taskstatus`, `ratingentry`, `habitlog`); index names follow `ix_<table>_<column>`.
- Datetimes are stored **naive UTC**. Convert at the boundary with `ensure_utc()`; never store local time.
- Date-only values stay `YYYY-MM-DD` strings (`assigned_date`, `date_str`) — that's the existing convention, follow it.
- `RatingEntry.target_id` + `target_type` is a deliberate polymorphic reference with no FK. New polymorphic references need a per-row translation step in any rebuild migration (see 0004).

## Safe vs unsafe changes on SQLite

| Change | How |
|---|---|
| Add a nullable column | `op.add_column` — safe, fast |
| Add a NOT NULL column | `op.add_column` with `server_default`, then backfill; a bare NOT NULL add fails on a non-empty table |
| Add / drop an index | `op.create_index` / `op.drop_index` |
| Drop a column | Modern SQLite supports `ALTER TABLE DROP COLUMN`, but not if the column is indexed or referenced — prefer a rebuild |
| **Change a column type** | **Rebuild.** SQLite cannot `ALTER COLUMN` |
| **Change a PK, add/remove a FK or constraint** | **Rebuild** |
| Rename a table | `op.rename_table` — but see the index gotcha below |

## The table-rebuild pattern

Worked, tested reference: **`src/timetrace/db/migrations/versions/0004_uuid7_primary_keys.py`**. Read it before writing a rebuild; it rebuilt nine tables and remapped every FK. The shape:

```python
def upgrade() -> None:
    bind = op.get_bind()
    bind.execute(sa.text("PRAGMA foreign_keys=OFF"))     # 1. FKs off for the duration

    op.rename_table("thing", "thing_old")                # 2. move the old table aside
    op.drop_index("ix_thing_name", table_name="thing_old")  # 3. SEE GOTCHA BELOW
    op.create_table("thing", ...)                        # 4. create the new shape
    op.create_index("ix_thing_name", "thing", ["name"])

    # 5. copy rows through a transform, then drop the old table
    for row in bind.execute(sa.text("SELECT * FROM thing_old")).mappings().all():
        data = dict(row)
        data["some_id"] = id_map[data["some_id"]]
        cols = ", ".join(data)
        binds = ", ".join(f":{k}" for k in data)
        bind.execute(sa.text(f"INSERT INTO thing ({cols}) VALUES ({binds})"), data)
    op.drop_table("thing_old")

    bind.execute(sa.text("PRAGMA foreign_keys=ON"))
```

### The index gotcha

`ALTER TABLE ... RENAME` **keeps existing indexes attached to the renamed table**. After `rename_table("thing", "thing_old")`, `ix_thing_name` still exists — now pointing at `thing_old`. Index names are global in SQLite, so `create_index("ix_thing_name", "thing", ...)` on the rebuilt table fails with "index already exists".

**Drop the old index off `<table>_old` before creating the same-named index on the rebuilt table.** 0004 does exactly this for `ix_taskstatus_name`, `ix_session_external_sync_id`, `ix_dayreview_date_str`, `ix_ratingentry_target_id`, `ix_ratingentry_target_type`, and `ix_habitlog_date_str`.

### Other rebuild rules

- **Order tables by dependency**: rebuild a parent before the children that reference it, and build every id map *before* you start renaming, so translations are available across tables.
- **Self-referential FKs** (`task.parent_id`) need the same map applied to both `id` and `parent_id` in one pass.
- **Polymorphic references** are not FKs and Alembic will not notice them. `ratingentry.target_id` needed its own `target_type`-switched translation. Grep for other string columns holding ids before you assume there are none.
- **`downgrade()`**: if the change is genuinely irreversible (id remapping, data loss), `raise RuntimeError` with a message pointing at the backup, as 0004 does. Do not write a downgrade that silently produces a different database.
- **Test on a copy first**, always:

```bash
cp ~/.timetrace/timetrace.db /tmp/tt-test.db
TIMETRACE_DB_FILE=/tmp/tt-test.db uv run timetrace db migrate
sqlite3 /tmp/tt-test.db "PRAGMA foreign_key_check;"       # must be empty
sqlite3 /tmp/tt-test.db "SELECT COUNT(*) FROM task;"      # compare against the original
```

Keep a dated backup in `~/.timetrace/backups/` before touching the real database.

## Two traps in this repo's Alembic setup

**1. Only `TIMETRACE_DB_FILE` redirects Alembic.** `db/migrations/env.py` defines `get_url()` as `return settings.database_url` and assigns it over the config in both offline and online mode. So `alembic.ini`, `-x` args, and `config.set_main_option("sqlalchemy.url", ...)` are all **ignored** — including in `run_migrations()`, which sets it pointlessly. Anything that thinks it is migrating a scratch database via `set_main_option` is actually migrating the user's real one. Use the env var, and remember `settings` is a module-level singleton read at import time.

**2. `alembic upgrade head` on a fresh database is currently broken at 0002.** `0002_add_task_statuses_and_subtasks.py:52-56` seeds the default statuses with `'created_at': sa.func.now()` in `op.bulk_insert`. SQLAlchemy's SQLite `DateTime` binder only accepts Python `datetime`/`date`, so it raises `TypeError: SQLite DateTime type only accepts Python datetime and date objects` and the run stops with the DB stamped `0001_initial_schema`. Existing databases are already past that revision and unaffected — but a from-scratch bootstrap does not work today. **Never put a SQL function in a bulk-insert value for a DateTime column; use a literal `datetime.now(UTC)`.**

## Indexing

The dataset is one person's tasks, sessions, and habit logs — thousands of rows, not millions. Don't over-index; each index costs write time and file size for a query that scans 3000 rows in under a millisecond.

Index when: the column is a FK you filter on constantly, a unique business key (`taskstatus.name`, `dayreview.date_str`), or an external lookup (`session.external_sync_id`). The existing indexes are already close to right.

Before adding one, prove it matters:

```bash
sqlite3 ~/.timetrace/timetrace.db "EXPLAIN QUERY PLAN SELECT * FROM session WHERE start_time >= '2026-08-01';"
```

`SCAN session` on a table with 40k rows is fine. `SCAN` inside a loop that runs per-task is not — that's an application-shape problem, fix the query rather than the index. See the `performance-profiler` skill.

## Do not

- Do not call `SQLModel.metadata.create_all()` outside the tests' in-memory engine. It bypasses Alembic and reintroduces the drift class of bug.
- Do not hand-edit the live database schema. If it happened anyway, write the migration that reconstructs what you did (that's what `0003_uuid7_and_sync_fields.py` is).
- Do not propose Postgres, migrations tooling other than Alembic, or a second database. `session.timezone` and the `externalsyncstate` table exist as groundwork for future sync — they are not a mandate to build it.
